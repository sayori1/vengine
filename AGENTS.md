# Architectural Invariants — VEngine

## 1. Основные принципы
- **Readability First** — читаемость важнее краткости кода.
- **KISS** — выбирать простейшую архитектуру, удовлетворяющую требованиям.
- **YAGNI** — не реализовывать функциональность на будущее.
- **Single Responsibility** — каждый класс отвечает за одну конкретную задачу.
- **Explicit over Implicit** — поведение и зависимости должны быть очевидными.
- **Composition over Inheritance** — предпочитать композицию, кроме случаев естественной иерархии типов.

## 2. Структура кода
- Один основной класс на пару `.h/.cpp`.
- Заголовки содержат интерфейсы, `.cpp` — реализацию.
- Методы должны быть небольшими и выполнять одну задачу.
- Избегать глубокой вложенности; предпочитать early return.
- Не создавать классы, интерфейсы и абстракции без практической необходимости.
- Не использовать макросы для генерации логики.
- Не создавать универсальные системы ради гипотетического переиспользования.

## 3. Naming
- Классы и типы: `PascalCase`.
- Методы и переменные: `camelCase`.
- Приватные поля: `snake_case_`.
- Константы: `kPascalCase`.
- Имена должны раскрывать назначение без необходимости читать реализацию.
- Избегать сокращений, кроме общепринятых (`id`, `dt`, `gpu`).

## 4. Ownership & Lifetime
- У каждого объекта должен быть очевидный владелец.
- По умолчанию использовать value semantics.
- `std::unique_ptr` — исключительное владение.
- `std::shared_ptr` — только при действительно совместном владении.
- Raw pointers и references — исключительно non-owning.
- RAII для ресурсов.
- Не допускать скрытого владения и циклических зависимостей.

## 5. API Design
- Минимальные публичные интерфейсы.
- Предпочитать строгую типизацию.
- Использовать `const` для неизменяемых данных.
- `enum class` вместо обычных enum.
- Избегать boolean parameters, если они ухудшают читаемость.
- Возвращать значения вместо output parameters, когда это разумно.
- Не использовать исключения для обычного control flow.
- Для ожидаемых ошибок использовать `std::expected` (C++23).

## 6. Performance
- Сначала корректность, затем профилирование.
- Избегать ненужных аллокаций и копирования.
- Использовать плотные структуры данных в hot paths.
- Не создавать отдельный `Node` для каждого вокселя.
- Виртуальные методы допустимы вне критических циклов.
- Не усложнять архитектуру ради неподтверждённых оптимизаций.
- Отделять data storage от processing в производительных системах.

## 7. Dependencies
- Минимизировать зависимости между модулями.
- Core не зависит от Renderer и Sokol.
- Node не зависит от Application.
- Voxel-модули не зависят от графического API.
- Внешние библиотеки подключать через `vendor/`.
- Не создавать глобальные mutable singleton-объекты.

## 8. Node Invariants
- Каждый Node имеет не более одного parent.
- Node эксклюзивно владеет своими children.
- Циклическая иерархия запрещена.
- Удаление parent уничтожает дочернее поддерево.
- Добавление и удаление children во время traversal должно быть безопасным.
- `onReady()` вызывается один раз при первом присоединении к активному дереву.
- `onDestroy()` вызывается один раз перед уничтожением Node.
- Порядок lifecycle должен быть детерминированным.
- `Node3D` хранит local transform; global transform вычисляется из иерархии.
- Изменение parent или local transform инвалидирует global transform.
- Владение Node не должно зависеть от его имени или пути.

## 9. Error Handling
- Ошибки программирования выявлять через `assert`.
- Ожидаемые ошибки обрабатывать явно.
- Не игнорировать возвращаемые ошибки.
- Не подавлять ошибки пустыми `catch`.
- Сообщения об ошибках должны содержать полезный контекст.

## 10. Code Quality
- Использовать `clang-format` с единым конфигом.
- Компилировать с `-Wall -Wextra -Wpedantic`.
- Debug: AddressSanitizer + UndefinedBehaviorSanitizer.
- Проверять инварианты автоматическими тестами.
- Комментарии объясняют **почему**, а не пересказывают код.
- Не добавлять комментарии к очевидным операциям.
- Не вводить новую архитектурную абстракцию без конкретного сценария использования.

## 11. LLM Development Rules
- Следовать существующей архитектуре и naming conventions.
- Не добавлять функциональность за пределами задачи.
- Не создавать fallback-реализации, скрывающие ошибки.
- Не дублировать существующую логику.
- Не менять публичные API без необходимости.
- Перед реализацией проверять существующие компоненты.
- После реализации обязательно собирать проект и запускать доступные тесты.
- Выбирать понятную реализацию вместо «умной».
- **Любое усложнение архитектуры должно иметь техническое обоснование.**
